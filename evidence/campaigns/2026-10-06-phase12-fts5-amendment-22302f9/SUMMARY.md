**Correction.** The 12.11/12.11b A1 lane *created* an FTS5 table but searched with
`blocks.text LIKE '%Q%'`; no receipt measured FTS5. This amendment adds a real
FTS5 surface to the A1 baseline and measures it at N ∈ {1,10,100,1000}. Two FTS5
tokenizers are measured: `unicode61` (whole-token) and `trigram` (substring). The
A1 search lane now uses `fts_tri MATCH` because the schedule's markers can be
embedded in a larger token (e.g. `theXF13A`), which a whole-token index misses.

Correctness (`raw/correctness.tsv`): LIKE and FTS5-trigram answer the expected
marker for all 12 documents; FTS5-unicode61 is recorded as-is (it misses
embedded-token markers). Per-query read bytes are the strace `read`+`pread64`
total for a batch of N fresh `sqlite3` processes (the lifetime court's A1 camera);
wall is that instrumented batch, so all variants pay identical strace overhead.

**Reading.** FTS5 resolves the marker through an inverted index; LIKE scans
`blocks.text`. On this small self-authored corpus both are dominated by the
per-query `sqlite3` process + database open, so the absolute numbers are close;
the table reports the measured difference, not an assumption. No claim is made
that FTS5 is faster in general.
