PHASE 28.6 DECISION — fragment locality (measurement only)

Historical control (Phase 22.5): VOLE selective read a median 3.15x more
bytes than page-level SQLite. This court re-measures, locally and exactly,
for five large documents: current VOLE closure vs a fragment directory's
minimum vs a page-level SQLite control.

SUMMARY
- current VOLE closure for a narrow request is a LARGE fraction of the whole
  source in every format (it reads the whole descriptor: 'full' descriptor
  read mode), exactly the Phase 22.5 mechanism.
- a fragment directory's floor+directory is >=10x smaller than the VOLE
  closure in 5/5 formats.
- that floor+directory is smaller than the page-level SQLite control (the
  page-mapped table) in 3/5 formats.
- exactness held: materialize --exact == source in 5/5.

DIRECTORY OVERHEAD (the deciding cost)
- the largest per-unit native directory is csv/native: 23,539,920 B for 490,415 units
  (48 B per source record/element) — larger than the source, so a
  per-unit structural index is NOT viable.
- csv: fixed_4096 directory 196,656 B vs fixed_65536 directory 12,336 B
- docx: fixed_4096 directory 26,832 B vs fixed_65536 directory 1,680 B
- json: fixed_4096 directory 196,656 B vs fixed_65536 directory 12,336 B
- parquet: fixed_4096 directory 196,656 B vs fixed_65536 directory 12,336 B
- pdf: fixed_4096 directory 426,624 B vs fixed_65536 directory 26,688 B

DECISION
  (1) YES — a fragment directory admits a MATERIAL bytes win over the
      current VOLE physical closure for narrow requests on large documents
      (5/5 formats >=10x smaller). The mechanism is that the current
      closure is the WHOLE encoded document, while a fragment directory
      needs the format-native unit plus a bounded COARSE directory.
  (2) BUT the win over page-level SQLite is NOT uniform: the fragment
      floor+directory beats the page-level control in only 3/5 formats.
      The ideal floor is tiny everywhere (a few bytes to ~62 KiB), but the
      directory needed to reach it is the binding constraint: a per-record
      index costs more than the file, and the fixed-size alternatives pay
      directory that grows as the fragment shrinks. For the row/record
      formats (CSV/JSON) a 4 KiB page-mapped SQLite is already competitive
      with any fragment scheme; fragmentation's wins are on PDF/DOCX (and
      marginally Parquet), where the native unit is a coarse structure.

  => 28.8+ is justified as a COARSE STRUCTURAL index (PDF objects/pages, ZIP
     members, Parquet row groups/column chunks) — NOT a per-record index and
     NOT a fan-out of tiny fixed fragments. For CSV/JSON the page-level
     control is not beaten on bytes+directory, so a fragmentation branch there
     must justify itself on something other than bytes (e.g. no source
     retention), or be dropped.
